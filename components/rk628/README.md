# RK628F/H bridge driver

For the Rockchip RK628H on the Waveshare HDMI to CSI Adapter (B), the Radxa 4K
HDMI IN to MIPI CSI-2 adapter and the WarpKVM boards. **Not run on hardware.**
It is written from the facts in Rockchip's GPL-2.0 Linux driver (no code taken,
see the top of `rk628_regs.h`) and does what that driver does, in the same
order.

It is linked into every image (about 14 KB) and registers itself like the other
bridges. `kvm_bridge_detect()` asks each driver in turn; this one answers only
when a chip at I2C 0x50 reads back the RK628F/H version word.

## How it fits

- **Detection is safe next to an EEPROM.** The ID read is one transaction: four
  address bytes, a repeated START, the read. An EEPROM at 0x50 takes the first
  bytes as its address and the rest as data to write, but it starts a write only
  on a STOP, and there is none before the read.
- **Lane rate.** The chip sends at 1296 Mbit/s per lane on two lanes, the only
  rate the Linux driver uses there (with hand-set D-PHY timings). It says so in
  `kvm_bridge_t.lane_mbps`, and the capture sets the CSI receiver to that rate,
  whatever the board's `CONFIG_KVM_MIPI_LANE_MBPS`.
- **Pixel format.** The chip sends only YUV422 (UYVY), which is what the rev 3.x
  images capture. The driver sets `kvm_bridge_t.yuv422_only`, and a rev 1.x
  image then captures YUV422 too and takes the LT6911D's reorder-for-JPEG path
  (`capture_pixfmt.c`): MJPEG only, H.264 shown as unavailable. That path was
  checked with the TC358743 sent to UYVY on a P4-ETH rev 1.3
  (`CONFIG_KVM_CAPTURE_TEST_YUV422`): the picture matches its RGB888 one, about
  7 fps at 1080p.
- **EDID.** The images and the name/ID patching live in `kvm_bridge`
  (`kvm_bridge_edid_build()`, generated by `tools/gen_edid.py`), shared with the
  TC358743.
- **Reset line.** The Radxa adapter puts RESETN on pin 5 of its 15-pin
  connector, the camera connector's CAM_GPIO. A board that holds that pin low
  keeps the chip in reset, and then nothing answers at 0x50.

## What a first tester should send

The log lines tagged `rk628` from start-up through plugging a source in: the
mode it reports (`MCU + I2C` expected), the chip and CSI versions, `source
WxH ... out WxH` or the reason it did not lock, and the `debug_bridge` line
(lock bits, TMDS clock, measured mode, CSI PHY status and error bits).

## Known gaps

- CEC uses the receiver's own controller (0x31f00) on GPIO1_B3. Whether a board
  wires the HDMI socket's CEC pin there is unknown: the Waveshare overlay for
  Linux leaves CEC off. The remote panel in the console shows up either way.
- Rev 1.x boards: MJPEG only, see above.
- The audio clock is set to 128 fs when the rate is known and the FIFO is
  reset if it runs over or dry. The Linux driver also trims the clock by 10 Hz
  steps to keep the FIFO half full; without that, expect an occasional click.
- 10-bit sources: the Linux driver uses the raw TMDS clock as the pixel clock
  on this chip, which is 1.25 times too high for 10-bit. Followed as is.
- Open questions the Linux driver does not answer: what the steps written to
  GRF 0x00f4 mean, and whether the chip's own MCU touches the receiver in
  "MCU + I2C" mode. A tester's log is the way to find out.
